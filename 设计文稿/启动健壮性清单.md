# 启动健壮性清单

从 2026-11-10 这一天里**五个真实启动失败**反推出来的规则。每条都对应一次真实事故，
不是理论。新增启动相关逻辑时逐条对照。

---

## 一、classpath 的三条铁律

### 1. 顺序：位置沿用 JSON 里**第一次出现**的那次，版本取最高

整合包 JSON 常把同一个库写两遍：先官方版本、后面再追加一份高版本。
去重时如果"跟最高版本走"，条目会被挪到末尾，**类加载顺序就变了**。

> 事故：1.12.2 实例，`log4j 2.15.0` 被从第 27 位挪到第 49 位 →
> Forge 的 `DeobfuscationTransformer` 被判定重入并永久停用 →
> Mixin 全部找不到命名类 → `NoClassDefFoundError: cgw`。

### 2. 身份：`group:artifact` **必须带上分类器**

`org.lwjgl:lwjgl-glfw:3.4.1` 与 `org.lwjgl:lwjgl-glfw:3.4.1:natives-windows`
是**两个不同的文件**。只用 `group:artifact` 当身份，natives 那份会被当重复库丢掉。

> 事故：Cleanroom 实例，9 个 LWJGL3 natives jar 被去重吞掉。

### 3. 互斥：同时有 LWJGL3 就不要 LWJGL2

Cleanroom / lwjgl3ify 用 LWJGL3 + `lwjglxx` 在 Java 层模拟 LWJGL2。
再放真的 LWJGL2（`org.lwjgl.lwjgl:*`）会互相遮蔽。

> 事故：Cleanroom 实例，`org.lwjgl.Sys` 来自真 LWJGL2 → 加载 `lwjgl64.dll` →
> Java 25 上 JVM 直接崩（`ClassFormatError: org/lwjgl/PointerWrapper`）。

另外：**OptiFine 的 jar 要排在 forge 之后**（它带着 deobf 命名的 forge 接口）。
> 事故：1.8.9 实例，`NoSuchMethodError: RegistryDelegate.getResourceName()`。

## 二、库解析：缺字段就按坐标推

| JSON 情况 | 处理 |
|---|---|
| 有 `downloads.artifact.path` | 直接用它 |
| 有 `downloads` 但没 `artifact` | 按 `group:artifact:version[:classifier]` 拼 maven 路径，**文件存在就用** |
| 完全没有 `downloads` | 同上 |
| `natives.windows` / 分类器 `natives-windows*` | 只取当前架构（跳过 arm64 / 32 位），既进 classpath 也解压 |

> 事故：Cleanroom 的 `com.cleanroommc:cleanroom` 没写 `downloads` → jar 被整段跳过 →
> `ClassNotFoundException: net.minecraftforge.fml.common.launcher.FMLTweaker`。

---

## 三、Java 选择

- JSON 的 `javaVersion.majorVersion` 优先；没有就按版本区间给默认值（老版本 8）。
- **Java 24+ 必须加** `--sun-misc-unsafe-memory-access=allow`，否则 LWJGL2 / 老模组
  在 `sun.misc.Unsafe` 上失败。低版本 JVM 不认这个参数，一定要按 `java_major` 判断。
- 需要"每个版本固定用哪个 Java"——目前只能全局选，是已知缺口。

---

## 四、参数拼装

- `arguments.jvm` / `arguments.game` 与 `minecraftArguments` **合并**再做占位符替换；
  两边都给 `--tweakClass` 时要按对去重，不能简单拼接。
- `--tweakClass` 顺序：FML 的 tweaker 永远在前，OptiFine 之类在后。
  顺序错会让 FML 用错 primary tweaker（历史上表现为 1.7.10 的 `Profiler` NPE）。
- 不要重复传同一类参数（`--versionType` 出现三次没有意义）。

---

## 五、启动前的自检（目前 + 计划）

已实现：

- 缺库检测：`info.missing` → 日志里列出来并提示补齐；
- 兼容处理说明：`info.notes` → 启动日志里打印"我们做了什么"
  （剔除了几个 LWJGL2、有几个库没写下载地址……）。

计划：

1. **classpath 不变量检查**：同一 `group:artifact:classifier` 只能出现一次；
   同一 natives 名称在不同 jar 里冲突时警告；
2. **natives 目录检查**：解压后与 jar 内清单比对，缺 DLL 就提示
   （`lwjgl64.dll` 缺失时 Java 只在运行期崩，很难查）；
3. **启动失败归类**：把退出码 + 最后 N 行日志 + `hs_err` 是否存在组合起来，
   给出"看起来是 Java 版本 / 原生库 / mixin 冲突"的判断。

---

## 六、排查方法（比读栈更快的顺序）

1. 先用**能启动的启动器**跑同一个实例，拿到它的**完整命令行**；
2. 逐项对比：JVM 参数 → classpath **集合** → classpath **顺序** → 游戏参数；
3. 三者都一样还崩，再读栈找 `Problematic frame` / `Caused by`。

> 这一天五个事故，全部是这个顺序在前三步就定位到的；直接读栈只会看到
> "Mixin 找不到类"这种下游症状。
