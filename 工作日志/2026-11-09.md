## 对照 MultiMC 后重做导航与框宽（15:10）

用户把我们的截图和 MultiMC 并排对比，觉得这一版"奇怪"，改之前反而不奇怪。逐条对着截图找原因：

1. **导航是一整块白色 listbox**：5 行挤在顶部、下面 400px 全白，像文件列表而不是侧边栏；
   选中是**系统蓝条**，和黑白灰主题直接冲突。
2. **框拉满窗口宽度**：页面宽 620、框到 864，但复选框只占一半，每个框右侧一大片空白，
   "框大内容小"看着像没做完。
3. **「样式设置」是个空框**：一行灰字配一个同样大的框，像坏掉。
4. 窗口 880x600 对这点内容来说过大。

**改动**

- 窗口 880x600 → 760x560；页面宽 620 → 520（框不再拉满，右侧留白一致）。
- 导航弃用 `listbox`，改成 5 个 `plus` 自绘项：行高 30、左内缩 12、
  选中浅灰 `#E4E4E4` + 近黑文字，未选中次要灰、悬停浅灰。
  （`listbox` 的选中色、行高、内缩都改不动，要改得做 `onDrawItem` 自绘，
  而 `drawItem` 的结构体 aardio 没给出文档，风险高——直接用 plus 更稳。）

  否则再细的线也会显得空。
- 系统控件的默认外观（列表选中蓝条）会直接破坏整个配色方案，
  能用自绘的场合优先自绘。

3. 问颜色有没有全部变量化（为深色模式 / 自定义主题准备）。

**改动**

1. 内容起始 `y 64 → 52`，标题 `16..46 → 14..42`（间距 18 → 10）。
2. 新增 `nav_highlight`（`bkplus`，0..200 宽），切页时 `setPos` 到选中项那一行。

   `bkplus` 画在窗体背景上，不会盖住文字。
3. `m3theme` 增加分区 token：`SIDEBAR / SIDEBAR_HOVER / SIDEBAR_SEL / FOOTER / DIVIDE /
   FRAME / FIELD / CARD` 及对应的 `C_*` COLORREF；`settings2`、`m3layout` 已全部改用 token。
   `m3theme.field()` 改为同时设文字色与底色（原来只设文字色）。

**关于"是否全部变量化"的实情（供深色模式评估）**

- ✅ 已变量化：凡是通过 `m3theme` 函数设置的颜色（plus 皮肤、静态文本、输入框），以及这次
  新增的三区 token。改 `m3theme` 开头那一段就能整体换色。
- ❌ 未变量化：**各窗体 DSG 里写死的 bgcolor，全工程 48 处**（窗体底 `0xF2F2F2`、

## 选中条乱飞与占位节丢标题（16:05）

**现象**（用户截图）

- 导航的选中条没落在选中行上，变成了导航面板右上角外面的一小块；
- 「样式设置」只剩一行说明，标题不见了。

**两个根因**

1. 选中条是用**一条** `bkplus` + `setPos(0, y, 200, 30)` 移过去的。
   `bkplus.setPos` 内部改的是 `this.$rect`（见 `lib/win/ui/ctrl/bkplus.aardio:239-247`），
   它的坐标系和 DSG 里的**逻辑像素不是一回事**，实测直接跑到面板外。
   → 改成每个导航项各配一条固定位置的 `bkplus`（0..200 × 行高），切页时用 `visible` 切换。
   只用「创建时坐标 + visible」这两条已经验证过的路径，不再碰 setPos。
2. `m3layout.close_section` 在 `plain` 分支里**提前 return**，把标题的创建一起跳过了。
   → 标题每次无序建；只有框按 `framed` / `plain` 决定画不画。
   （`bkplus` 画在窗体背景、`static` 是窗口，标题永远在框线之上，绘制顺序不影响。）

**教训**

- 又一次"按文档理解 API 就上手"：`setPos` 看起来是同一个控件移动，但它底下走的是设备坐标
  的矩形，和多处的逻辑坐标混用。**能不动坐标系就别动**——用固定位置 + 显隐更省心。
- 提前 return 的写法容易连累同一函数里的其它副作用（这里把标题一起干掉了；
  另一个工具其实是想跳过"画框"）。

**待办**

- 用户再看一眼导航与占位节。

## 导航双高亮：去掉"选中条"这个概念（16:25）

**现象**

- 截图里同时出现两条高亮：当前页「Java 管理」一条，上一页「账户管理」还留着一条。

**根因**

- 选中条是**独立的 bkplus**，靠 `visible` 切换隐藏。切页时它那块父背景没有完整重绘，
  上一个选中条就留在原地。这类"两个独立控件要保持同步"的写法本身就容易残留。

**改法（结构性）**

- 干脆不要"条"：导航项本身就是 **0..200 的整行宽度**，用 `plus` 的 `paddingLeft = 16`
  把文字往里推。选中 / 悬停的底色天然通到两边，**一个控件搞定，不可能残留**。
- `plus` 确实支持 `paddingLeft / paddingRight / paddingTop / paddingBottom`
  （`lib/win/ui/ctrl/plus.aardio:42-54`，影响文本矩形 `:346-354`），这个以后可以常用。

**教训**

- 凡是"两个控件要一直保持同步"的设计（一条跟着另一条移动、一个跟着另一个显隐），
  都改成"一个控件承担两件事"。少一个状态，就少一类 bug。

**待办**

- 用户验：悬停应是一条通到两边的浅灰带；切页后不留残影。

## 分组框改成"只包内容，标题在框外"（16:45）

**用户的要求**

> 参考 MPC，它的框是把内容包起来的，标题虽然在框里但不会让框空出一大截；
> MultiMC 也是这样。我倾向 MultiMC 那种：**标题在外面，框里是内容**。

**问题**

- 之前是"标题压在框线上"（MPC 的经典 group box）：框的上边必须从标题下面开始，
  于是标题占掉框顶一段，框里凭空多出一截空白——正是"框空出来一大截"。

**改动（`lib/m3layout.aardio`）**

- 框的上边界 = 内容顶 `- GROUP_PAD_Y(10)`；下边界 = **最后一行底** `+ GROUP_PAD_Y`。
- 删掉 `GROUP_TOP_ON`（原本用来把框线压到标题下方 10px）。
- `SECTION_GAP 8 → 12`：标题与第一行之间拉开 12px，其中 10px 被框上边占掉，
  视觉上标题下 2px 开始是框线。
- **`make()` 记录本节内容的真实底边 `max(bottom)`**：框底不能拿"下一节起点"推算，
  因为行高 24、行距 30，每节末尾都会剩 6px，每个框底部就会多出半行。
- 标题字号 `-12 → -13`，当小标题用。

**教训**

- 分组的"包围盒"要用**子元素的真实边界**算，不能用流式游标的当前值（那个值含行距余量）。
- 两种 group 风格（标题压线 / 标题在外）不是随便换的：标题压线时，框顶必然被标题吃掉一段，
  如果内容又少，就会出现"框大内容小"。标题在外时框可以严格贴内容。

**待办**

- 用户看框与内容的贴合度；`GROUP_PAD_Y` 10 可以按观感调。

**现象**

- `m3layout.check()` 统一从 `L.left + L.label_w` 开始排，但复选框**没有标签**，

## 别人打不开发布版：先查 exe 里到底有没有库（22:40）

**用户反馈**

> 我发布的 exe 别人没法直接打开，显示没法导入 MMMLC 库。

**机制（`docs/specs/aproj.md:61,79-81`）**

- `libEmbed="true"` 时，工程引用的 aardio 库会被**编译并内嵌**到 exe 里，
  PE 资源类型名 `LIB`，资源名是**库命名空间的大写**（`MMMLC` → `MMMLC`）。
- 窗体源码内嵌为 `DLG/NAME.AARDIO`（大写）。
- 所以正常情况下，别人不需要装 aardio、不需要任何 lib 文件夹。

**检查了工作区里全部 6 个 exe**

- `MMMLC` **全部都在**（包括 11-05 那份 dist）。
- 11-05 那份缺 `M3LAYOUT`、`DLG/SETTINGS2.AARDIO`、`DLG/LAYOUT_TEST.AARDIO`——
  因为它们是 11-09 才出现的，属正常。

**结论**：用户发出去的那份 exe **不是工作区里这 6 份中的任何一份**（或打包时选错文件）。
下一步要他拿实际那份跑一遍检查。

**新增工具 `tools/check-publish.ps1`**

- 扫描 exe 字节里的 UTF-16 资源名，逐项报告库与窗体是否内嵌（`[ OK ]` / `[MISS]`）。
- 清单来源：`lib/*.aardio` → 大写库名；`dlg/*.aardio` → `DLG/NAME.AARDIO`；外加共享库 `MMMLC`。

## 发布版报 bad constant in precompiled chunk（23:05）

**对方看到的原始报错**

```
{File}:main.aardio        {Line}:#12
{Error}:import MMMLC failed :

{File}:~\lib\MMMLC.aardio {Line}:#18
{Error}:import console failed !syntax error:
console: bad constant in precompiled chunk
```

**这句话是什么意思**

- `~\lib\...` 说明加载的是**内嵌**在 exe 里的库（不是磁盘上的）。
- `bad constant in precompiled chunk` 是 Lua/aardio 的字节码装载错误：**内嵌的预编译块
  字节对不上**（块的类型标记读不出来）。
- 常见成因：①发布用的 IDE 与 exe 里带的运行时**版本不一致**（例如 aardio 刚更新、
  还用旧进程发布）；②exe 在传输/被杀软处理时被改写。

**查证**

- `aardio.exe` 的修改时间是 **11-05 21:41**（当天更新过），而那两个 exe 是 21:49 / 23:17 发布的——
  时间贴着，很可能是**更新后没有重启 IDE 就发布**。
- 工程 `.build/` 缓存是 10-31 的旧文件，也可能是因素之一。

**本轮改动**

- `core/launch/MMMLC.aardio`：**去掉 `import console`**。这个库一行 `console.*` 都没用，
  GUI 也不需要控制台。报错位置正是这一行（原第 18 行），去掉它至少少一个可坏的预编译资源。
  这不是根因修复，是把无谓依赖清掉。

**给用户的操作顺序**

1. 跑 `tools\deploy-core-lib.bat` 把新 MMMLC 部署到 aardio 用户库；
2. **完全退出 aardio 再重新打开**（11-05 更新过），删掉 `launcher\MMMLauncher\.build`；
3. 重新「工程 → 发布」；
4. **先在本机双击** `dist\MMMLauncher.exe`（别用 F5），确认能起来；
5. 跑 `pwsh -File tools\check-publish.ps1`，全 `[ OK ]` 再发；
6. 发人时**打包成 zip**，不要传裸 exe——聊天软件或杀软改写文件也会造成这类"块损坏"。

**补充：是不是被杀软改坏了？**

- 大概率**不是**。杀软的行为模式是"删除 / 隔离 / 启动时拦下 / SmartScreen 提示"，
  它不会让程序正常启动、再只把里面某个字节码块改坏——那要求它定向改写 PE 资源，实际不会这么做。
- `bad constant in precompiled chunk` 是"对所有人都坏"的错，最可能是 11-05 那次
  aardio 更新后没重启 IDE 就发布造成的。
- 决定性判断：**在本机双击同一个文件**。
  - 本机也报同样错 → 构建问题，与对方无关；
  - 本机正常 → 才轮到传输 / 杀软。

**顺带验了用户 22:39 重新发布的那份**

- `dist\MMMLauncher.exe` 2626 KB（sha256 `271F7CD7…E474FCC`）。
- `tools\check-publish.ps1` 结果 **RESULT: OK**：全部库（含 `MMMLC`、`M3LAYOUT`）
  与全部 17 个窗体（含 `DLG/SETTINGS2.AARDIO`、`DLG/LAYOUT_TEST.AARDIO`）都在。
- 下一步要用户**双击这份**确认能起来；能起来就把 11-05 那份从分发渠道撤掉。

var THIN_SCROLLBAR = false;   // settings2.aardio 顶部

改成 `true` 后 F5 立刻生效，只作用于 Java 列表与 JVM 参数输入框。
