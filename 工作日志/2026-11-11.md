**结论**

- 「专一」成立：所有增长都在"让任何整合包能正确地起来"这条线上，
  三件套的边界没破（core 不下载、launcher 不嵌游戏逻辑、下载器尚未开工）。

  但设置抽屉有 8 页、版本覆盖 7 个键、另有一个 Mod 子页。
- 复杂度里有一部分是**换可靠性**（兼容各种不规范 JSON，方向正确），
  另一部分是**换功能**（Mod 管理、日志筛选），后者若继续长就会偏离 slogan。

**建议的判据**（待用户确认后再写进设计文档，不擅自改）

1. 新功能先过三问：让"启动"更可靠吗？不做会不会导致启动失败？能否放进独立工具？
2. 给"简单"量化：主页交互元素 ≤ 3；设置页数上限；版本覆盖键上限。
3. Mod 管理不再长大（不做批量安装 / 搜索 / 更新检查），未来可并入下载器或独立工具。
4. 正版与外置登录只占「账户管理」一页，不扩散成皮肤 / 好友 / 服务器列表。

## 追问：还算 minimalist 吗（21:10）

**结论**：按"交互与运行"算，按"功能面与代码量"不算；两者都要认，不能只挑有利的那个。

**通过的六条（可测）**

1. 首屏决策数 2（选版本、点启动），0 个必填设置；
2. 打扰 0：无广告、无推送、无强制登录、无自动更新弹窗、无遥测；
3. 单 exe、无运行时依赖、portable（删目录即卸载）；
4. 不看文档能启动；
5. 可预测：同样输入同样结果，不因更新改变行为；
6. 状态全在目录里（`config.json` + `versions`），无注册表、无隐藏状态。

**不通过的三条**

1. 11,135 行，其中与"启动"无直接关系的约 1,500–2,000 行（mod / toml / zip / 崩溃规则）；
2. 设置 8 页、`settings2.aardio` 3,409 行；
3. **真实使用中设置页是常态路径**：昨天五个实例的排查，每次都要开「Java 管理」「路径与版本管理」「版本独立设置」。
   这条最要紧——它推翻了"深度藏在设置里所以无害"的辩护。

**判断**

minimalism 不是存量而是**流量**：等于"拒绝了多少"，不是"现在有多少"。
昨天接受得多（日志筛选、Mod 页长大）、拒绝得少，拒绝率在下降。

**待用户决定**（不擅自改设计文档）

- slogan 精确化：`专一且克制`，或给 minimalism 三条可测注解；
- 「一进一出」配额：每加一页 / 一个覆盖键 / 一个按钮，必须删或合并一处；
- 把 v2 第 177 行已有的「外置成独立小工具」思路升级为通用规则。

## 追问二：好用与最初设想（21:25）

**用户观点**：它依然好用；但确实在偏离最初设想，而最初的设想来自"对启动器制作不了解"。

**判断**

1. 「好用」成立，而且是修出来的，不是堆出来的：昨天五个实例全部启动成功，
   代价是五条兼容规则（去重保位、分类器进 key、有 LWJGL3 去 LWJGL2、
   缺 downloads 按坐标补、Java 24+ 放行 Unsafe）——**合计约 120 行**。
   现象极复杂、代码极轻，这正是 minimalism 的正确形态：把复杂度**压缩成规则**，
   而不是**摊开成界面**。
2. 最初的设想是个**假设**："启动很简单，所以启动器可以很小"。
   昨天的工作证伪了前半句：启动本身不简单（JSON 不规范、加载器混装、类加载顺序、JVM 代际）。
   但**后半句仍然有效**：不简单的事实应该被启动器吸收，而不是转嫁给用户。
3. 所以漂移的不是"目标"，是"复杂度的落点"：兼容知识落进 core（对）；
   Mod 管理落进启动器（可商量）；日志筛选落进界面（可接受但不增加可靠性）。
4. v2 第 15 行自己写了退路：「精简不等于简陋：不以牺牲可定制性与美观为代价」。
   现在的状态是这句话的后半句赢了前半句——不是背叛文档，是文档内部的张力兑现了。

**建议的落点规则**（待用户定）

- 复杂度预算：`core/` 不设上限（换可靠性）；主页/通知/首屏 零增长；设置页 一进一出。
- 「Minimalism」只用来约束**界面与干扰**，不再用来声称**功能范围**。

## 资源管理要不要独立成工具（21:55）

**用户判断**：拆出去会更简洁，但好像没必要。

**同意，但理由要换**：判断标准不是"拆了启动器变轻"，而是"**拆了会不会打断用户的闭环**"。

- 资源管理不是独立任务，是**启动前的就地修复**：
  启动 → 崩 → 禁用/换一个模组 → 再启动。拆成两个程序就断在这个回环中间
  （切窗口、传路径、重新选版本）。
- 拆出去还要额外承担：共享配置与路径、版本选择同步、双份打包与测试、
  以及"用户得先知道该开哪个"——正好增加决策数，与 minimalism 背道而驰。
- 收益却很小：600 行 + 1 个子页，换不回上面的成本。

**真正该拆的是"资源获取"而不是"资源管理"**

| 需求 | 启动器内 | MMM-DL | 独立工具 |
|---|---|---|---|
| 看 / 启用 / 禁用本地 mods，标重复与缺前置 | ✓ | | |
| 浏览 / 搜索 / 下载 / 更新 / 依赖解析 | | ✓ | |
| 改界面外观与布局（创作者向） | | | ✓ |
| 崩溃后定位可疑模组 | ✓ | | |

判据三条：不启动游戏时会不会反复打开它；它是否需要自己的主界面；拆开是否打断已跑过两次以上的回环。

**更好的简化方向**：不是拆文件，是减**决策数**。
例如崩溃窗口的「疑似模组」直接给「禁用这一项」按钮，把"两页操作"压成"一次点击"——
这比拆工具更能守住 minimalism。

**待办**（待用户决定，不擅自改设计文档）

- 把上表与三条判据写进 `设计文稿/设计文档v2.md` 的「二、三件套」边界；
- 资源管理冻结在当前范围（本地状态 + 就地修复），出现浏览 / 搜索 / 下载三个动词即转 MMM-DL。

## 原始目标（给整合包作者做只启动的启动器）怎么找回（22:10）

**用户补充**：最初只想做"只能启动游戏 + 基本设置"的启动器，结果做成了全能型，又觉得删不掉。

**判断：原始目标没丢，缺的不是"删功能"，是一份「随包声明」**

整合包作者真正要的不是"功能少"，而是：
玩家双击就能进；改不坏关键设置；崩溃时能把日志交回来。
现在这四件事里，前三件要靠"作者能锁住设置"，而启动器**没有任何按包下发的入口**——
所有设置都是玩家在界面里改，作者只能写说明文档。

**提案：同一份代码，两种呈现**

| | 作者模式（检测到随包声明时） | 玩家模式（现在） |
|---|---|---|
| 主页 | 版本固定，不显示版本下拉 | 版本下拉 + 启动 |
| 设置 | 只剩「关于 / 诊断」，锁定的项置灰并注明 | 全部 8 页 |
| 崩溃 | 一键打包 + 作者指定的反馈方式 | 现有崩溃窗口 |
| 锁定的项 | 内存 / Java / 窗口 / JVM 参数 / 关闭文件校验 | 玩家可改 |

- 新增第三个边车文件 `.m3l-pack.json`（作者随包分发），
  与 `.m3l-meta.json`（下载器写的元信息）、`.m3l.options.json`（版本独立设置）并列，互不合并；
- 没有该文件 → 完全按现在的行为，零回归；
- 作者模式的开关控制在 5 个以内，**没有自己的界面**（就是一个 json）。

**为什么"删不掉"是正常的**

现在的 Mod 列表、崩溃规则、日志打包、按版本 Java，全部是**支援工具**：
玩家说"起不来"时，作者要能回答"禁用这个试试 / 把日志发我"。
删掉它们不是回到极简，是回到"作者没法支援玩家"。所以正确的动作是**分层默认值**，不是截肢。

**纪律**

- 新功能默认属于玩家模式；作者模式只增"锁定项"，不增界面。
- 任何进入作者模式首屏的东西，必须能回答："它让玩家更少操作吗？"

## 别的启动器也做这么多健壮性吗（22:20）

**证据（从本机日志里实测，不靠印象）**

成熟实现的 JVM 参数（同一次 Cleanroom 启动）：**37 个**，其中

- `--sun-misc-unsafe-memory-access=allow`、`-XX:+UseCompactObjectHeaders` —— JDK 24+ 适配，正是我们昨天补的那条；
- `-Dlog4j.configurationFile=versions/打脸日常/log4j2.xml` —— 给单个实例指定 log4j 配置；
- `-XX:MaxNodeLimit=… -XX:TieredCompileTaskTimeout=… -XX:NmethodSweepActivity=1` —— 治"老版本 Forge + 新 JVM 编译卡死"；
- `-Dfml.ignoreInvalidMinecraftCertificates`、`-Dfml.ignorePatchDiscrepancies` —— 与我们相同；
- RMI/JNDI codebase 关闭 —— Log4Shell 加固；
- classpath 120 项（含全部架构的 natives jar），另有 `-javaagent:authlib-injector…`。

**对照我们的五条特例：对方都有对应物**

| 我们的规则 | 对方的做法 |
|---|---|
| OptiFine 排到 classpath 末尾 | 追加 OptiFine tweaker，并重排库 |
| log4j 保留首次位置 | 直接塞 `-Dlog4j.configurationFile` |
| 有 LWJGL3 就剔 LWJGL2 | 支持 lwjgl3ify，带全部架构 natives |
| 缺 downloads 按坐标拼 | 一律按 name 拼路径 |
| Java 24+ 放行 Unsafe | 同一条 flag |

**为什么"我们看起来特例更多"**

1. 知识是**反向获得**的：我们从崩溃日志推规则，他们从多年 issue 攒补丁；
2. 我们是**通用解析器**（吃任意 JSON），他们维护**已知特殊表 + 修复动作**；
3. 他们**能下载、能修**（缺库/Java 版本直接补），我们只能**检测 + 解释**，
   于是代码长成了诊断逻辑；
4. 我们**把处理写进日志**（「已剔除 2 个 LWJGL2」），他们静默 —— 可见性差异被误读成复杂度差异。

**要分清两类特例**

- 生态的：跨 1.7.10→Cleanroom(Java 25)、3 种加载器、2 套 LWJGL 的兼容规则 —— 承诺"任何包都能起"就要继承；
  五条规则合计约 **120 行**，`core` 仍只有 1,048 行。
- 我制造的回归：meta 与 path 错位、分类器没进 key、`InvalidateRect` 传 null —— 三次，属于实现失误，不属于生态复杂性。

**结论**：它们做的至少一样多，只是不说；我们的特例数 ≈ 承诺支持的生态宽度。
想真正减少特例，方向是**收窄承诺**（随包声明），不是继续堆规则。
