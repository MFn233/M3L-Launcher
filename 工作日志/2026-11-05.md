## 许可证兼容性：MIT 与 GPLv3 是单向兼容（21:55）

**结论**

- **MIT → GPLv3：兼容**。MIT 代码可以进 GPLv3 项目，整体按 GPLv3 分发。
- **GPLv3 → MIT：不兼容**。不能把 GPLv3 代码改许可证成 MIT，衍生作品只能继续 GPL。
- 换句话说：兼容性是**单向**的，方向决定了义务，不是"互相兼容"。

**对本项目的意义**

- 现状：`about.aardio` 和 `设计文稿/design.md` 都写着 MIT，但工程里**没有 LICENSE 文件**。
- 崩溃原因分析那套规则（`lib/m3crash.aardio` 的 23 条）是照着 HMCL 的
  `CrashReportAnalyzer.java`（GPL-3.0-or-later WITH AdditionRef-HMCL）翻写成 Lua 模式的。
  从版权角度，规则清单的**选择与编排**属于受保护的表达，直接改写通常算衍生作品。
- 因此在源码里既写 MIT、又在鸣谢里承认"参考 GPL-3.0 实现"，是**自相矛盾**的：
  鸣谢不构成 GPL 合规，GPL 要求的是许可证、源码与声明。

**两条出路（待用户选择）**

1. **改成 GPL-3.0-or-later**：一处声明 + 加 LICENSE 文件即可；诚实、省事，但与"独立项目、随便拿去用"的初衷有冲突。
2. **重写规则表**：不照 HMCL 的清单，改为从真实崩溃报告和公开发布的游戏日志格式里自行归纳，
   写完删掉鸣谢里的 HMCL 行——这样 MIT 才站得住。工作量大一些，但是"干净"的那条路。

**待办**

- 等用户决定走哪条；在此之前不动许可证声明。

## 原生界面的能力上限（00:15）

用户问：只用 m3theme + plus 自绘 + win.form，最多能改到哪、哪些注定改不了。

**查证到的事实**（`docs/library-guide/std/win/ui/ctrl/plus.md`、`canvas.md`）

- plus 是 **GDI+ 自绘控件**，支持：字体图标、jpg、透明 gif、**动画 gif**、半透明 png、九宫格贴图、
  进度条、边框圆角、五种自绘事件（`onDrawBackground` / `onDrawForeground` / `onDrawString` /
  `onDrawBorder` / `onDrawComplete`）以及动画接口（`startAnimation` / `onAnimation`）。
- canvas 是常驻 PARGB 内存画布，**跟随显示器刷新（60Hz → 16.7 ms）**，自绘代码把 `cls` 从 plus
  改成 canvas 即可复用；默认不透明，`orphanWindow(true)` 可做分层透明窗口。
- 实测数据（文档给的，200% DPI、880×1360）：plus 每帧 24 ms / 间隔 31 ms；canvas 每帧 5 ms / 16.7 ms。

**结论：上限比预想的高**

- 可做到：自绘按钮/开关/标签页/进度条/徽标、圆角卡片、渐变、贴图与图标、自绘滚动条、
  无边框窗口 + 自绘标题栏、**60fps 动画**（用 canvas）、九宫格缩放图标。
- 做不到（本质限制）：
  1. **系统绘制且不给自绘的部分**：下拉框弹出层的边框与阴影、菜单、工具提示、richedit 内部滚动条、
     listview 表头的部分细节、trackbar 滑块（形状只受 `border.radius` 约束）。
  2. **文本输入**：自绘输入框等于重造 IME/选区/右键菜单/撤销，不现实；只能继续用 edit/richedit。
  3. **窗口合成效果**：真亚克力/毛玻璃（DWM 未公开接口）、任意形状阴影、跨窗口淡入淡出。
  4. **硬件加速**：GDI+ 是 CPU 绘制，大范围模糊/多层半透明叠加代价高。
  5. **无障碍**：自绘控件对读屏软件等于空白，除非另做 UIA。
  6. **排版精度**：没有字距/行高/字体回退栈，彩色 emoji 渲染不出来。

**对 m3theme 的重新定位（重要）**

- 现在的 m3theme 只是"配色表 + skin 快捷函数"；真正的上限要靠**自绘**打开，
  所以它应该升级成「**自绘原语库**」：圆角矩形/渐变/阴影/图标等绘制函数 + 每种控件一个 helper
  （内部用 onDraw* 实现）+ 尺寸与间距 token（现在只有颜色，没有尺度）+ 统一动画节拍（canvas）。

## 界面"苏联美学"的成因与改法（00:40）

用户反馈：现在的界面像苏联美学，但不是初衷，而且不知道怎么改。

**诊断（都能指到具体代码）**

1. `m3theme.aardio:46` 主按钮 `border = { color = INK; width = 1; radius = 0 }` ——
   **直角 + 1px 纯黑描边**，是"工程图纸/控制台"感最强的两个信号。
2. 白底黑框按钮 + 悬停整块反黑（`:44-45`）—— 老式工业按钮的观感。
3. 全窗口 `BG = #F2F2F2` 平铺（`:13`），控件却用白底，**层次反过来**了：
   现代做法是"白底 + 浅灰卡片"，现在是"灰底 + 白控件"，看着像一块块贴上去的。
4. 字号层级太窄：`-11 / -12 / -13`（说明、正文、按钮几乎同大），标题只有 `-16/-18` 两处，
   整体**视觉平坦**，没有主次。
5. 间距没有尺度：控件普遍 8~10px 相邻，卡片与区块之间没有 16/24/32 的节奏。
6. 分隔线 `#D8D8D8` 偏重（`:15`），把界面切成一格一格的"表格"。
7. 没有任何"焦点"：全是灰字白框，眼睛不知道先看哪。

**改法（按"改动量/收益"排序）**

1. **圆角**：按钮 8、卡片 10~12、输入框 6（`radius = 0` → `8`）。仅此一条就能去掉大半"硬"。
2. **去掉 1px 描边**，用底色差分组：底 `#F4F4F5`、卡片 `#FFFFFF`、悬停 `#EFEFF1`；
   线只在必须分隔时用，且降到 `#ECECEC`。
3. **一个实心焦点**：主按钮黑底白字（无边框、radius 8），其余按钮全部"无底无框纯文字"，
   悬停才给浅灰底。现在的"所有按钮都长一样"是最像控制台的地方。
4. **字号拉开**：22（页面标题）/ 14（区块标题，半粗）/ 13（正文）/ 12（说明）。
   去掉 `-11`，说明文字也用 12。
5. **间距 token**：4 / 8 / 16 / 24 / 32。控件高：按钮 36、输入 32；卡片内边距 16、卡片间距 16。
6. **可选**：极淡投影（GDI+ 可画）或 1px `#EFEFEF` 内描边，让卡片"浮"起来。

**三个可选方向（都仍是黑白灰，不加彩色）**

- **A. Windows 11 设置风**（推荐）：白卡 + 浅灰底 + 大圆角 + 实心黑主按钮。最容易做对。
- **B. 日式留白**：纯白底、几乎无框、超大留白、只有字号层级，靠空气分组。
- **C. 终端深色**：#111 底 + #E5E5E5 字。辨识度高，但更"硬"，有再次变成苏联风的风险。

**待办**

- 等用户选方向；选定后先在 `theme_test` 里做"改前 / 改后"一屏对照，确认再套到真窗口。

## m3theme 圆角改版试了又撤（01:20）

**做了什么**

- 按方向 A（Windows 11 设置风）改了一版 m3theme：圆角 8/12、去描边、按钮分
  primary（实心黑）/ button（白底）/ ghost（纯文字）/ danger，加尺度 token，13 个窗口各留一个 primary。
- 用户实测后**观感更差**，要求回退 → `git revert`（提交 `8863102`），工程回到直角 + 1px 描边那一版。

**为什么回退（用户的原话，也是关键发现）**

- 「按钮改成圆角后，一些原生的内容显得格格不入，它们改不了圆角」。
- 结构性问题：`plus` 是自绘控件，可以任意圆角；但 `edit` / `combobox` / `checkbox` /
  `listview` / 滚动条 / 表头都是**系统绘制**，圆角改不了。
  圆角按钮和方角系统控件并排，等于两种设计语言混在一起，比全方角更难看。

**结论（重要，避免下次再犯）**

- **混用系统控件时，方角是唯一自洽的选择**；圆角只在"全部自绘"的前提下才成立。
- 原来的"苏联感"不是方角造成的，而是另外三件事：**1px 纯黑描边**、**所有字一样大**、**控件密排无节奏**。
  所以下次要改，只改这三件，不碰圆角：
  1. 描边 `INK` → 极淡（`#E5E5E5`）或直接去掉，靠底色差分组；
  2. 字号拉开（说明 / 正文 / 区块 / 标题四档）；
  3. 间距按 8 的倍数给呼吸（卡片内 16、块间 24）。
- 如果哪天真要圆角，唯一前提是把 edit / combobox / checkbox / listview 全部换成 canvas 自绘——
  那是另一个量级的工程，不是改主题能解决的。

**踩坑**

- 回退时被安全网拦了两次：`git checkout <ref> -- <path>`（覆盖工作区）和 `git restore <path>`
  （丢弃未提交改动）。改用 `git stash push -- <file>` 保住草稿，再 `git revert --no-commit` 老实地撤销提交。
- stash 里还留着当时的日志草稿（`stash@{0}: log-draft-theme`），不影响工作区。

**待办**

## 列表列宽下限：子类化这次行得通（01:45）

**做了什么**

- `lib/m3list.aardio` 新增 `limit_width(ctrl, min_width)`：
  - `::SendMessageInt(hwnd, 0x101F /*LVM_GETHEADER*/, 0, 0)` 取表头句柄；
  - `win.subclass(ctrl, ...)` 子类化 **listview 本身**（不是表头），拦 `WM_NOTIFY`；
  - `HDN_ITEMCHANGING(-320)`：`mask & HDI_WIDTH` 且 `cxy < min` → **返回 1 否决这次变化**；
  - `HDN_TRACK(-328)`：把 `pitem->cxy` 直接改成 `min`（双保险）；
  - 结构体用 `raw.define` 按偏移读：`NMHEADER`（`pitem` 在偏移 20）、`HDITEM`（`mask`、`cxy`）。
- 接入五个列表：版本 / Java / 路径 / 账号（下限 56）、崩溃窗口日志列表（80）。

**为什么这次能行**

- 之前 `onnotify` 与 `translateCommand()` 都不生效，根因是：`WM_NOTIFY` 的 `hwndFrom` 是**表头**
  （listview 的子窗口），aardio 在 `win/ui/_.aardio` 分发时按控件句柄查不到就丢弃了通知。
- 子类化拿到的是**原始消息**，不经过那层分发；而且否决发生在**拖动过程中**，
  所以手感是"到下限就停住"，而不是以前定时器方案的"弹回来"。

**踩坑 / 风险**

- `win.subclass` 的约定：回调返回非 null 就短路（`win/subclass.aardio:15-17`），
  返回 null 才会 `CallWindowProc` 链回原过程。我只在否决时返回 1，其余路径都返回 null。
- 双击分隔线自动适配（`HDN_DIVIDERDBLCLICK`）没有处理，可能把列压到下限以下；需要时再补。
- 未在真机验证过。

**待办**

- 用户 F5 后拖动表格列宽：到 56 应停住、拖宽不受限制；确认后再决定要不要把下限调大或按列分别设。

## 放弃列宽下限，撤回子类化（02:30）

**做了什么**

- lib/m3list.aardio：删掉 limit_width()、	race() 以及为它们引入的
  import fsys / fsys.file / win.api / win.subclass，只留 it() 与 min_width_of()。
  头注释改成"试过三次都没成，已放弃"，并写明现状：靠每次打开窗口重排版保证布局。
- 五个窗口（版本 / Java / 路径 / 账号 / 崩溃）去掉 m3list.limit_width(...) 调用。

**为什么**

- 用户实测：打开带列表的窗口**直接卡死**，而且列宽下限本身始终没生效。性价比太低，撤掉。

**踩坑（这次卡死的教训）**

- 最可能的原因：	race() 在 WM_NOTIFY 里对**每一条通知**做一次"打开文件 → 写 → 关闭"，
  而 listview 打开时会发成百上千条通知（每个单元格一条 LVN_GETDISPINFO 之类）。
  在窗口过程里做文件 I/O，UI 会被彻底堵住。
- 结论：**永远不要在 WNDPROC / 消息回调里做文件或网络 I/O**。要诊断就先把信息攒在内存里，
  等一个明确的时机（比如按钮点击、窗口关闭）一次性落盘。

**关于这个功能的总账**

- 试过四条路：onnotify（通知到不了）、	ranslateCommand()（同样到不了）、
  定时器事后纠正（手感差，用户否掉）、子类化 + HDN_ITEMCHANGING 否决（无效，且诊断卡死）。
- aardio 的 listview 是系统控件，表头通知既拿不到也拒不了；再往下就要写回 cxy 内存，
  属于不安全操作。**判定：不划算，不做。**
- 现有保障：it() 每次打开窗口按可视宽度重排；拖动弄乱了关掉重开就恢复。
