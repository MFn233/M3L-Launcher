## 许可证兼容性：MIT 与 GPLv3 是单向兼容（21:55）

**结论**

- **MIT → GPLv3：兼容**。MIT 代码可以进 GPLv3 项目，整体按 GPLv3 分发。
- **GPLv3 → MIT：不兼容**。不能把 GPLv3 代码改许可证成 MIT，衍生作品只能继续 GPL。
- 换句话说：兼容性是**单向**的，方向决定了义务，不是"互相兼容"。

**对本项目的意义**

- 现状：`about.aardio` 和 `设计文稿/design.md` 都写着 MIT，但工程里**没有 LICENSE 文件**。
- 崩溃原因分析那套规则（`lib/m3crash.aardio` 的 23 条）是照着 HMCL 的
  `CrashReportAnalyzer.java`（GPL-3.0-or-later WITH AdditionRef-HMCL）翻写成 Lua 模式的。
  从版权角度，规则清单的**选择与编排**属于受保护的表达，直接改写通常算衍生作品。
- 因此在源码里既写 MIT、又在鸣谢里承认"参考 GPL-3.0 实现"，是**自相矛盾**的：
  鸣谢不构成 GPL 合规，GPL 要求的是许可证、源码与声明。

**两条出路（待用户选择）**

1. **改成 GPL-3.0-or-later**：一处声明 + 加 LICENSE 文件即可；诚实、省事，但与"独立项目、随便拿去用"的初衷有冲突。
2. **重写规则表**：不照 HMCL 的清单，改为从真实崩溃报告和公开发布的游戏日志格式里自行归纳，
   写完删掉鸣谢里的 HMCL 行——这样 MIT 才站得住。工作量大一些，但是"干净"的那条路。

**待办**

- 等用户决定走哪条；在此之前不动许可证声明。

## 「两个 core」的命名歧义（22:50）

**问题**

- 现有的 `core/` 实际指「**启动**核心」（MMM-C）。
- 用户还想要一个「**下载**核心」，同样是可被别的项目 embed 的无界面库。
- 于是「core」这个词同时指两个东西——目录名在描述**角色**（core），而不是**功能**（launch / download），
  角色相同就会撞车。

**结论（建议，待用户拍板）**

- 保留 `core/` 作为**类别**（无界面、可 embed 的代码都住这里），第二层按**功能**分：
  - `core/launch/` —— MMM-C：`MMMLC.aardio` + `MMMLCore/`（命令行工程）
  - `core/download/` —— 下载核心：`MMMDLC.aardio`（将来）
- 库名成对：**`MMMLC`**（MMM Launcher Core）与 **`MMMDLC`**（MMM Download Core），
  和产品代号 MMM-C / MMM-DL 对得上，不会和 GUI 产品名混。
- 界面工程保持在根：`launcher/`、`downloader/`。
- 不提前抽象「两个核心共享的底层」：等真的重复第三次再抽 `MMMU` 之类，现在抽是猜。

**待办**

- 等确认后执行 `git mv`：`core/MMMLC.aardio → core/launch/MMMLC.aardio`、
