## 一、今天做了什么

### 1. 摸清现状，修 core 的 bug

先读了 `1.txt` 和工作区结构（core / launcher / downloader 三块）。core（`core/MMMLCore`）原本是个 CLI，实测跑不通，逐条修掉：

| 问题 | 原因 | 处理 |
|---|---|---|
| `{Attempt to call}: table` | 把 `table` 当函数迭代（`for k,v in find_placeholders(x)`） | 先赋值再迭代 |
| Java 版本识别失败 | 用了 Lua 的 `(.-)` 惰性量词，aardio 没有 | 改成 `'version "([^"]+)"'` |
| `${auth_player_name}` 变成重复 N 遍 | `string.split` 的多字符分隔符是**字符集**语义 | 改成手写 `indexOf`/`slice` 替换 |
| classpath 里混进 arm64/x86 natives | 没按 `natives-windows-arm64` 之类过滤 | 加 `is_our_native` 判断 |
| 游戏窗口不显示 | `process.popen` 默认 `_SW_HIDE` | 显式 `showWindow = 1` |
| Ctrl+C 后留下孤儿 java | 没绑作业对象 | 加 `killOnExit()` |
| 日志文件丢失尾部 | 缓冲 | 改成每行 flush |

CLI 契约也补齐了：`--game-dir/--version/--username/--memory/--java/--work-dir/--uuid/--access-token/--user-type/--version-type/--width/--height/--log-file/--no-wait/--dry-run/--help`，退出码 0–4。

**验证结果**：`1.12.2-OptiFine_G5`（Java 8）能从 CLI 正常启动到 `Stopping!`、退出码 0；`Fabulously Optimized`（Java 21）能解析并启动，但卡在实例自己的 Distant Horizons（`Cannot unpack libzstd-jni`），判定为实例/环境问题，不是启动器问题。

### 3. 今天踩到并修掉的坑

这些是真实运行时炸出来的，记下来避免重复：

1. **`plus.setCueBannerText` 必须在 `editable = true` 之后**  
   否则内部 `owner.editBox` 还是 null，在 `plus.aardio:1617` 抛错。

2. **`combobox.add()` 没有返回值**（`listbox.add` 才有）  
   `setItemData(combobox.add(x), ...)` 会传 nil，炸在 `combobox.aardio:233`。  
   解决：不要用 `setItemData/getItemData`，用平行数组记住每项对应的值。

3. **`winform.add({...})` 里漏写控件**  
   路径窗口漏了 `listPaths`，一进 `render()` 就是「索引 null」。  
   已加静态检查脚本：把每个窗口的 `winform.xxx` 引用和 `add()` 里声明的控件名对一遍。

4. **`var` 只对声明之后的代码生效**  
   函数里用到的 `var buffer` 如果声明在函数后面，函数会把它当全局（nil）。  
   所有状态变量统一提到文件最前面。

5. **各窗口整份回写配置会互相覆盖**  
   路径窗口拿的是打开时的旧配置，关闭时一 `save(cfg)` 就把 Java 管理刚存的列表抹了。  
   解决：`m3config.save_keys(cfg, keys)`，每个窗口只写自己的字段。

6. **数组删除会留 null 洞**  
   `table.remove` 之后 JSON 里出现 `null` 元素，下次读出来是空条目。  
   解决：读的时候 `m3config.compact()` 清一遍。

7. **`plus` 控件不派发 `onRightMouseUp`**  
   那是 `win.ui.tracker` 的事件，plus 只在 `notify` 打开时挂 tracker，而自动启用列表里没有它。  
   解决：右键改成**可见的「停止」按钮**（设计文档的原始要求本来就是「启动后显示一个按钮」）。

8. **列表重建会清空选中项**  
   `render()` 里 `clear()` 之后 `selIndex` 归零，第二次点按钮就没对象可操作。  
   解决：按值（路径/目录）记住选中项，重建后找回。

顺带修掉一个语法坑：aardio 的双引号字符串是**原始字符串**，`"\""` 实际是「一个反斜杠 + 一个空串」，不是引号；判断 PATH 条目是否带引号要写 `'"'`。

### 为什么 aardio 是 32 位

- 实测本机 `aardio.exe` 的 PE 头 Machine = `0x014C`（x86），它生成的 `MMMLCore.exe` 也是 x86；安装目录里没有 64 位编译器/运行时。
- 所以不是我们选了 32 位，而是**这套工具链只产出 32 位**。
- 后果：WOW64 重定向——`ProgramFiles` → `Program Files (x86)`、`System32` → `SysWOW64`、`HKLM\SOFTWARE` → `Wow6432Node`；进程地址空间受限；不能加载 64 位 DLL。
- 绕法：读 `ProgramW6432`、用 `fsys.wow64.disableRedirection(回调)`、用 `fsys.wow64.process()` 启动 64 位程序。
- 对启动器无碍：它不把 MC 载进自己的进程，只是 `CreateProcess` 一个 64 位的 `java.exe`。

## 事故与修复：MAX_PATH 截断（10-30 23:40）

**现象**：把版本重命名成 105 个字符的超长名字，弹出 `RAW CALLBACK ERROR`：
`lib\fsys\_.aardio:174  trimRight(fullpath(null))` → 参数是 null。

**根因**：Windows 路径上限 **260 字符**。完整路径是 `<versions>\<名字>\<名字>.json`，
105 字符的名字算下来是 **268** 字符：

```
目录  ...\versions\<名字>              157  ✓
json  ...\versions\<名字>\<名字>.json  268  ✗
```

`io.joinpath` 超限时**静默截断**（返回的路径被砍短，而不是 null），于是：

1. 目录改名成功（157 字符没问题）；
2. json / jar 被改成**截断后的 90 字符名字**；
3. 文件夹名和 json 名对不上 → 版本彻底读不出来。

**修复磁盘**：把目录改回 `Fabulously Optimized`，json / jar 同步改名，
并把 JSON 里的 `id` 改回 `Fabulously Optimized`。现在两边一致。

**代码加固**：

- 新增 `max_name_length()`：按当前游戏路径算出名字上限，
  公式 `(250 - #versions目录 - 7) / 2`（名字在路径里出现两次，另外算上两个反斜杠和 `.json`）。
  当前 `test\.minecraft` 下大约是 **97** 个字符。
- 重命名前先把 src / dst / old_json / new_json / old_jar / new_jar **全部算出来**，
  任何一个为 null 或长度 ≥ 250 → 直接拒绝，**一个文件都不动**。
- 删除前也判一次 null。
- 非法字符检查改成逐字符比对（不再用 pattern，避免转义坑）。
- 已存在的长名字不受影响：只在不主动重命名的时候保持原样。

- 加固：`open_log_window` / `notice` 用 `try{...}catch(e){...}` 包住——
  缺日志窗体时照常启动（只是没有日志窗口），缺提示窗体时退化成状态栏文字，不会再「什么都不发生」。

**教训：aproj 不能手改（10-31 00:50）**

- 我手改的 `default.aproj`（10 个窗体 + MFn/0.1.0.0 元信息）被 IDE **整份覆盖**回只含 `settings.aardio`，
  版本号也被改成 0.0.0.3。原因是工程管理器里打开着的工程不会同步硬盘修改，
  关闭工程 / 保存文档时会用内存里的配置写回（`docs/specs/aproj.md:146`）。
- 正确做法（同文件 `:152`）：在工程视图里右键对应目录 → **「同步本地目录...」**，
  IDE 会扫描磁盘、把新增文件补进工程树；工程属性（版本号、公司名）也只能在 IDE 里改。
- 所以以后新增 dlg 文件后，要么让用户手动同步，要么改完 aproj 再重开工程。
