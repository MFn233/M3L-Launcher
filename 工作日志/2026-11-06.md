## 分组框抢 Z 序（00:20）

**现象**

- 设置（原型）打开后看着正常，**鼠标一移到右侧，整块内容被盖住**，分组标题只剩上半截。

**根因**

- 分组框用 plus 画。plus 是**交互控件**，aardio 文档明确写过这条
  （docs/guide/ide/system-prompt.md:1674）：

  > bk 与 bkplus 都是无句柄背景控件，在父窗体背景上绘图，适合作为其他控件的背景。
  > 其他具有交互样式的控件在激活焦点时会改变 Z 序遮挡其他控件。

  鼠标进入 plus 框 → 它升到 Z 序顶端 → 它那块填充色把内容全盖掉。

**改法**

- 8 个分组框 cls 由 plus 改为 kplus；边框改用创建参数
  order={color=0xDCDCDC;width=1}、底色 gcolor=0xF2F2F2；
- 删掉运行时调 skin 的 rame() 函数（kplus 没有 skin 方法）；
- 分页切换照旧：kplus 自己实现了 isible（内部 $hidden + edraw，见
  lib/win/ui/ctrl/bk.aardio:296-319）。

**踩坑**

- 这条是**判断性错误**而不是 API 记错：把"能画边框和底色"当成了"可以用作背景"。
  背景类控件在 aardio 里是 k / kplus 这一类**无句柄**控件；凡是能交互的控件
  （plus / utton）都可能抢 Z 序，不能当背景用。

**待办**

- 用户 F5 后再试：鼠标在右侧任意移动，内容不应再被盖住；
- 分页切换时确认另外两页的分组框不会残留（不应出现幽灵边框）。

## 合并设置窗口的体积账（23:45）

用户问：把所有管理窗口压进 settings2，体积上有没有收益。

**实测数据**

| 项 | 数值 |
|---|---|
| 发布产物 dist\MMMLauncher.exe | 2570 KB |
| 全部 dlg/*.aardio 源码 | 101.8 KB |
| settings + 四个管理窗体（java/paths/versions/accounts） | 49.2 KB |
| 控件数：settings2 现在 / 合并后 | 50 → 约 90 |

**结论：体积收益是 0**

- 合并只是把代码**挪位置**，不是删代码；能省下的只有每个窗体重复的 import 与窗体样板，
  估算 1~2 KB，占 exe 的 **0.05%**，肉眼不可见。
- exe 的 2.5 MB 主要是 aardio 运行时与标准库，几个窗体的源码在噪声级别。
- 就算改成"直接删掉四个 dlg、功能不做"，也只省约 35 KB（1.4%），不值得为体积改架构。

**真正的代价（被问的这一面）**

- 一个窗体 90 个控件：打开时全部创建，比现在慢；GDI 对象更多。
- 单个 DSG 文件会涨到 1300 行左右，IDE 设计器操作变笨重。
- 维护时"一改全动"，回退粒度变粗。

**真正的收益（合并的唯一理由）**

- 交互一致：所有设置在一个窗口里，不再有"打开设置 → 再弹一个窗口 → 再弹一个窗口"的层级。

## 为什么 HTML 好看、winform 难看（00:10）

用户观察：同样的东西，我用 HTML 设计出来好看，转成 winform 就难看。诊断如下。

**1. 布局机制不同（最大原因）**

- HTML：flex / grid / padding / gap / line-height 全是**自动**的，我只声明关系，浏览器算像素。
- winform：**绝对坐标**。每个控件手填 left/top/right/bottom，没有 gap、没有 padding 概念；
  行距要自己算，控件高度与字号的关系要自己凑。手算误差 ±2~4px，十几个控件叠起来就"歪"。

**2. 排版资源不同**

- CSS 有 line-height、letter-spacing、ont-weight: 500、系统字体栈。
- LOGFONT 只有**字高**和**两档字重**（400 / 700），行高不可设（多行只能塞 \r\n）。
  结果：层次只能靠字号拉开，稍不注意就"一片字一样大"。

**3. 系统控件不受控**

- dit / combobox / checkbox / listview 有固定的内缩、边框、焦点框；
  我只能给外形尺寸，文字起点和垂直位置由系统决定 → 标签与控件很难真正对齐。
- HTML 里每个盒子都完全受我控制。

**4. 我没有渲染反馈（根本原因）**

- HTML 的规则是确定的：数值 → 结果一一对应，我按规范写基本不会歪。
- winform 的坐标、DPI 缩放（逻辑像素 vs 设备像素）、控件内缩都是**隐式规则**，
  我看不到渲染结果，只能猜。猜错就歪，而且歪得很有"手工感"。

**结论：不是审美问题，是"缺少自动布局 + 缺少反馈"。**

**对策（明天落地）**

1. 在 aardio 侧写一个极小的布局助手（m3layout）：按 8 的网格自动算 	op，
   只用「声明顺序 + 类型 + 高度」摆放，不再手算每个坐标：

`ardio
var L = m3layout(24, 56, 536);          // 左边距、起始 top、可用宽度
L.section("账号");                       // 分组标题 + 分隔线
L.row("user"; 32);                       // 一行：标签 + 控件 + 按钮
L.row("memory"; 32);
L.done();
`

2. 固定三种"行模板"（标签+输入框 / 标签+下拉 / 说明行），以后所有页面复制模板，
   不再每行手动对齐。
3. HTML 原型配一张**数值表**，值直接写成 winform 能用的单位（x/y/w/h、字号、颜色）。
4. 你 F5 后**截图给我**——这是最快的闭环，我按图修 4px 的偏差，比我再猜一轮准。

- 明天顺序：内容清单 → 两套 HTML + 数值表 → 你选 → 写 m3layout → 生成设置页。
