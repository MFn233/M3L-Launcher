## 设置窗口打开慢（12:20）

**现象**

- 打开设置时窗口"加载一下"才完整出现。

**原因（按代价排序）**

1. **七个页面的控件在 `loadForm` 期间一次性全建**：约 90 个窗口控件 + 8 个 bkplus + 7 个导航项。
2. **打开时就把四份数据全渲染了一遍**：账户、Java、路径、版本。
   其中版本列表要逐个版本读 JSON；更贵的是 `list_version_names()` 里对**每个版本**
   都跑了一次 `m3version.repair()`（读 JSON + 可能写回，纯磁盘 I/O）。
3. **鸣谢页**在打开时往 richedit 灌了 12 行带颜色的文本（每次 appendText 都要重排）。

**这一轮的改动（只做 2 和 3）**

- 新增 `ensure_page(n)` + `page_ready` 表：账户(3) / Java(4) / 路径版本(5) / 鸣谢(7)
  改为**第一次切到该页**时才准备；
- 初始化里不再预渲染这四页；
- `list_version_names()` 去掉逐版本 `repair()`——启动前 `main` 已经对当前版本自愈过；
- 鸣谢正文包成 `credits_fill()`，由 `ensure_page(7)` 触发。

**为什么没动第 1 条**

- 控件懒建要把七页的构建代码各自包成函数，改动面大、风险高；
  先把数据准备挪走，看剩下多少再说。

**怎么判断剩下的是哪一类**

- 只在 **F5** 里慢、发布版不慢 → 是对话框源码在 IDE 下每次重新编译，属于正常；
- **发布版也慢** → 才是控件创建的开销，那时再做懒建。

**顺带**

- `default.aproj` 被 IDE 重写了一次（加了 UTF-8 BOM），内容和之前一致，无需处理。

## 关于页版本号改为 m3app.version_text()（12:50）

**用户的诉求**

- 关于页的版本号改成"纯检测 exe"，别再有判断逻辑——否则每次测试都要先发布、或者手动改对话框里那行字。

**为什么不能真的"纯读 exe"**

- F5 跑的是 aardio 宿主 exe，`fsys.version.getInfo(io._exepath)` 拿到的是工具套件自己的版本
  （45.x），所以那个"认产品名"的判断不能删——删了 F5 会显示 45.0.0.0，更糟。

**实际做法：把版本号收进一处常量，做成两个来源的兜底**

- 新增 `launcher/MMMLauncher/lib/m3app.aardio`：
  - `VERSION = "0.2.0"`（只写前三位）；
  - `PRODUCT = "M^3 Launcher"`；
  - `version_text()`：能读到自己的 exe 版本资源就返回它，否则返回 `VERSION`。
- `dlg/settings2.aardio` 的关于页改为 `P6.text("版本 " ++ m3app.version_text(), true)`，
  删掉对话框里写死的 "版本 0.2.0"，也删掉初始化里那段重复的读取代码。

**代价与配套**

- 升版本现在要改两处：工程属性 `FileVersion`（四段）+ `lib/m3app.aardio` 的 `VERSION`（前三位）。
  已写进 `AGENTS.md` 的工程/发布一节与 `待办临时.txt`。
- `tools/check-publish.ps1` 增加版本一致性检查：对比 aproj 前三位与 `m3app.VERSION`，
  不一致打 `[WARN]`（不影响退出码）。

**验证方式**

- F5：关于页应显示 `0.2.0`（来自常量，不再依赖发布）；
- 发布版：显示 exe 资源里的三位版本（与工程属性一致）。

## 设置该立即保存还是点保存才存（13:10）

**用户的问题**

> 玩家改了半天设置，结果点了「取消」，那不就难受了？

**现状是"混合"，这才是真问题**

| 页面 | 现在的行为 |
|---|---|
| 启动器设置 / 游戏设置 | 暂存，点「保存」才写盘；点「取消」丢弃 |
| 账户管理 / Java 管理 / 路径与版本管理 | **每个操作立即写盘**（列表操作没法暂存） |

于是用户无法预测"我这一下到底存没存"——同一个窗口里两种语义。

**两条出路**

A. **全部立即保存**：去掉「保存/取消」，底部只留「关闭」；改动立刻生效，
   底部提示「已保存」；文本输入在失焦（或回车）时写盘；破坏性操作仍保留确认框。
   代价：**没有撤销**（除非以后单独做"恢复默认"）。
B. **全部暂存 + 取消时若脏则确认**：语义统一为"保存/取消"，
   点取消时若有未保存改动，弹「有未保存的修改，确定放弃？」。
   代价：列表操作（删账号、删版本）本来就必须立即生效，语义仍会有一部分不统一。

**倾向 A**：和四个管理页一致、没有"忘记保存"、也没有"取消误伤"；
四个管理页已经证明立即写盘在这个应用里是可行的。

**待用户决定**，决定后再动 `dlg/settings2.aardio` 的按钮与各控件的保存时机。

## 设置改为「草稿暂存 + 保存合并」（13:40）

**用户定的模型（原话）**

> 暂存修改的内容到临时文件，如果点保存，就合并；如果取消时检测到有内容修改了，
> 就询问是否取消；如果选择了取消，回退设置。

**实现**

| 位置 | 改动 |
|---|---|
| `lib/m3config.aardio` | 新增 `draft_path()` / `load_draft()` / `save_draft()` / `clear_draft()`，草稿文件 `config.pending.json`（与 `config.json` 同目录） |
| `dlg/settings2.aardio` | 值类控件改动 → `mark_dirty()` 写草稿（**不碰 config.json**）；保存时"重读 + 覆盖 + 写回 + 删草稿"；取消时若有草稿先确认；打开时若有残留草稿就套到工作副本并提示 |

- **保存为什么先重读**：这一会儿别处可能改过列表数据（删账号、切路径、切版本），
  直接写整份旧快照会把这些改动冲掉。所以先 `m3config.read()` 拿最新的，
  只把草稿里的**值类键**覆盖上去。
- **列表类操作仍然立即生效**：删账号、删版本、设为当前路径/版本本身就是"提交动作"，
  没有"暂存"的意义。
- **`loading` 守卫**：初始化时程序化设置下拉框会触发 `onSelChange`，
  那时不能写草稿，否则用户什么都没改、点取消却会被问"有未保存的修改"。

**行为一览**

- 改设置 → 底部不提示，草稿静默写盘；
- 点保存 → 合并写入，关窗；
- 点取消（或 Esc / 关闭）→ 有草稿才问「有未保存的设置修改，确定放弃吗？」，
  选「取消」留在窗口，选「确定」丢弃草稿并关闭；
- 强关/崩溃 → 下次打开会恢复草稿并提示。

**待办**

- 用户验：改几个开关 → 取消 → 应被询问；改完保存 → 重开应保持；
  手动造一个 config.pending.json 看恢复提示。
- 以后可以把「恢复默认」做成按钮，弥补"没有撤销"。

## 路径/版本子页：去掉闪烁、加序号列、修挤压（15:10）

**原因与改法**

1. 闪烁是我在"已在该子页"分支里又调了一次 `sub_apply()`——那会把整页几十个控件

   旧配置里存的列宽没有序号列，恢复时在头上补一个；默认列宽也收到 504 以内，
   否则 `m3list.fit` 会等比例压缩，把序号列压得只剩一条缝。

- 保存时把三个列表的列宽（Java / 路径 / 版本）一起写回配置；以前只记住 Java 的。

**待办**

## 行号列收进 m3list：setup(list, cols, bool)（16:10）

**用户的要求**

- 不是"给用户一个开关"，而是 API 上用一个**布尔参数**决定这个列表要不要「#」列。

**做法（`lib/m3list.aardio`）**

```aardio
m3list.setup(list, cols, true)   // 第三个参数 true = 最前面插一列 #
m3list.renumber(list)            // 每次重填列表后按显示顺序重编号
m3list.fit(list)                 // 超宽时等比压缩
```

- `setup()`：布尔为 true 时插「#」列（传入的 cols 已带 # 就不重复插），
  并用**句柄做键**记住这个列表开了行号（不往控件上挂自定义属性）。
- `renumber()`：只在开了行号的列表上生效，否则直接返回——
  防止误把列表真正的第一列改成数字。
- 为什么行号不能只是一个"列外观开关"：列宽可以一键加，但每行的数字得跟着数据走，
  所以是 setup（列）+ renumber（内容）两步。

**调用点**

- 路径 / 版本 / Java 三个列表都开行号；
- 账号列表只有一两行，不加（加了只是噪音）。
- 删掉之前手写的 `path_seq` / `ver_seq` 计数器，以及"恢复列宽时补 # 列"的分支——
  列宽合并逻辑收进 `setup()` 一处。

**顺带**

- 三个渲染函数末尾各加一次 `m3list.renumber(...)`。
- AGENTS 的界面约定补了一条：列表统一走 `m3list` 的 `setup` / `renumber` / `fit`。

**待办**

- 用户验：三个列表的 # 列都从 1 连续编号；拖动列宽后保存、重开仍保留。

## bug：不同目录的同名版本共用隔离状态（16:40）

**现象**

- 两个 `.minecraft` 里都有同名版本（比如都叫 `1.12.2`）时，改其中一个的隔离状态，
  另一个也跟着变。

**根因**

- `cfg.shared` 只用**版本名**做键：`cfg.shared["1.12.2"] = true`。
  但"要不要隔离"本来属于「某个目录下的某个版本」，用名字做键就把不同目录混在一起了。

**改法（`lib/m3config.aardio`）**

```aardio
shared_key(dir, name)                  // 小写目录 ++ "|" ++ 版本名
is_isolated(cfg, dir, name)            // 没记录 = 隔离
set_isolated(cfg, dir, name, bool)     // 只写 true / 删键，不存 false
normalize_shared(cfg)                  // 读配置时把旧的裸名字键迁到当前游戏目录
```

- `settings2` 的四处（判断 / 切换 / 重命名 / 删除）都改走这套接口；
- `main.aardio` 启动时的隔离判断带上 `cfg.game_path`。

**为什么键里用 `|`**

- Windows 文件名不允许 `|`，所以「目录 + 版本名」拼起来不会产生歧义。

**兼容旧配置**

- 旧表里是裸版本名，`normalize_shared()` 读的时候迁到**当前游戏目录**上。
  这样升级后原来的隔离设置不会一下子全失效（虽然同名跨目录的情况本来就分不清）。

**没有改的部分**

- `cfg.version`（当前版本）仍然按名字记——它本来就是"当前选中的版本名"，
  切路径时会校验该目录下是否存在，不存在就自动换一个。

**待办**

- 用户验：两个目录放同名版本，分别开关隔离，互不影响；重开设置后状态保持。
